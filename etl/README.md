# ETL Documentation: Dimension and FactSales Loading

This document describes the ETL process used to load the rental data warehouse from the operational rental database.

The ETL is implemented as SQL Server stored procedures in the script:

```text
/etl/SQL-ETL-procedures.sql
```

The script loads the warehouse tables in the `RentalDW.MiniProject` schema from the operational source tables in the `RentalOperationsDB.MiniProject` schema.

## Project Context

The mini-project contains two database layers:

| Layer | Database | Schema | Purpose |
| --- | --- | --- | --- |
| Operational database | `RentalOperationsDB` | `MiniProject` | Source system for rental transactions, customers, locations, equipment, and maintenance records. |
| Data warehouse | `RentalDW` | `MiniProject` | Reporting layer using a star schema with dimension tables and the `FactSales` fact table. |

The ETL process transforms the normalized operational database into a dimensional model that is easier to use in Power BI and analytical SQL queries.

The fact grain remains:

```text
One row in FactSales = one rented physical item on one rental transaction line.
```

This means a rental transaction with three rented items creates three rows in `FactSales`.

## Stack

- SQL Server / SSMS
- T-SQL stored procedures
- Operational source database: `RentalOperationsDB`
- Data warehouse target database: `RentalDW`
- Power BI as the reporting layer

## ETL Overview

The ETL process is procedure-based. Each warehouse table is loaded by a separate stored procedure, and a wrapper procedure runs the full load in the correct order.

| Procedure | Target table | Main purpose |
| --- | --- | --- |
| `MiniProject.usp_Load_DimDate` | `DimDate` | Generates the calendar date dimension for the reporting period. |
| `MiniProject.usp_Load_DimCustomer` | `DimCustomer` | Loads new customers from the operational database. |
| `MiniProject.usp_Load_DimGeography` | `DimGeography` | Loads new rental locations from the operational database. |
| `MiniProject.usp_Load_DimItem` | `DimItem` | Loads new rentable items with model, category, and latest maintenance context. |
| `MiniProject.usp_Load_FactSales` | `FactSales` | Loads new rental transaction lines as fact rows. |
| `MiniProject.usp_Run_Full_ETL` | All target tables | Runs all dimension loads first, then the fact load. |

The ETL is designed as an insert-only incremental load for new business records. Existing warehouse rows are not currently updated if source data changes.

Future improvement:

```text
Use MERGE statements for Type 1 updates or implement SCD Type 2 logic for historical dimension tracking.
```

## ETL Control Table

The script creates an ETL control table if it does not already exist:

```sql
CREATE TABLE MiniProject.ETL_Control (
    procedure_name NVARCHAR(100) NOT NULL,
    last_run       DATETIME      NOT NULL,

    CONSTRAINT PK_ETL_Control PRIMARY KEY (procedure_name)
);
```

The table stores one row per ETL procedure.

| Column | Description |
| --- | --- |
| `procedure_name` | Name of the ETL stored procedure. |
| `last_run` | Timestamp of the most recent successful procedure run. |

The script initializes the table with one row for each load procedure:

| Procedure name | Initial `last_run` value |
| --- | --- |
| `usp_Load_DimDate` | `2024-02-01` |
| `usp_Load_DimCustomer` | `2024-02-01` |
| `usp_Load_DimGeography` | `2024-02-01` |
| `usp_Load_DimItem` | `2024-02-01` |
| `usp_Load_FactSales` | `2024-02-01` |

Design notes:

- `ETL_Control` is mainly used by `usp_Load_FactSales` to identify new rental transactions since the previous run.
- The dimension procedures update `ETL_Control.last_run`, but they mainly rely on `NOT EXISTS` checks instead of `last_run` filtering.
- The control table supports repeatable ETL runs and makes the incremental load state visible for debugging and validation.

## Full ETL Execution Order

The wrapper procedure `MiniProject.usp_Run_Full_ETL` executes the load procedures in this order:

```text
1. usp_Load_DimDate
2. usp_Load_DimCustomer
3. usp_Load_DimGeography
4. usp_Load_DimItem
5. usp_Load_FactSales
```

This order is important because `FactSales` depends on surrogate keys from the dimension tables.

The fact load performs lookups into:

- `DimCustomer`
- `DimDate`
- `DimGeography`
- `DimItem`

Therefore, dimensions must be loaded before fact rows can be inserted.

## Stored Procedure Details

### `MiniProject.usp_Load_DimDate`

Loads the `DimDate` table.

#### Source

`DimDate` is generated by the ETL script. It is not loaded from the operational database.

#### Target

```text
RentalDW.MiniProject.DimDate
```

#### Load logic

The procedure:

1. Deletes rows from `DimDate`.
2. Generates a calendar date range from `2024-02-01` to `2026-12-31`.
3. Inserts one row per date.
4. Derives common calendar attributes.
5. Updates `ETL_Control.last_run` for `usp_Load_DimDate`.

#### Target columns

| Target column | Logic |
| --- | --- |
| `date_key` | Generated sequential key using `ROW_NUMBER()`. |
| `date` | Calendar date. |
| `year` | `YEAR(date)`. |
| `quarter` | `DATEPART(QUARTER, date)`. |
| `month` | `MONTH(date)`. |
| `week` | `DATEPART(WEEK, date)`. |
| `day` | `DAY(date)`. |

#### Notes

- This is a controlled calendar load rather than a source-based incremental load.
- The current script deletes and reloads `DimDate`. If fact rows already reference `DimDate` through foreign keys, this may fail unless constraints and load order are handled carefully.
- A safer production pattern is to pre-populate `DimDate` once and later append only missing future dates.
- The date range must cover all `rental_start` and `rental_end` dates that may be loaded into `FactSales`.

### `MiniProject.usp_Load_DimCustomer`

Loads new customer records into `DimCustomer`.

#### Source

```text
RentalOperationsDB.MiniProject.Customer
```

#### Target

```text
RentalDW.MiniProject.DimCustomer
```

#### Load logic

The procedure:

1. Reads the current maximum `customer_key` from `DimCustomer`.
2. Selects customers from the operational `Customer` table.
3. Inserts only customers that do not already exist in `DimCustomer`.
4. Generates new surrogate keys using `MAX(customer_key) + ROW_NUMBER()`.
5. Updates `ETL_Control.last_run` for `usp_Load_DimCustomer`.

#### Source-to-target mapping

| Target column | Source / logic |
| --- | --- |
| `customer_key` | Generated warehouse surrogate key. |
| `customer_id` | `Customer.customer_id`. Operational alternate key. |
| `first_name` | `Customer.first_name`. |
| `last_name` | `Customer.last_name`. |
| `address` | `Customer.address`. |
| `city` | `Customer.city`. |
| `country` | `Customer.country`. |
| `email` | `Customer.email`. |
| `phone` | `Customer.phone`. |

#### Incremental behavior

New customers are identified using:

```sql
WHERE NOT EXISTS (
    SELECT 1
    FROM MiniProject.DimCustomer dc
    WHERE dc.customer_id = c.customer_id
)
```

This makes the customer load insert-only and idempotent for existing `customer_id` values.

#### Notes

- Existing customer rows are not updated if address, city, email, phone, or name changes in the operational database.
- Future improvement: use `MERGE` for Type 1 updates or add SCD Type 2 columns if customer history is required.

### `MiniProject.usp_Load_DimGeography`

Loads rental location data into `DimGeography`.

#### Source

```text
RentalOperationsDB.MiniProject.RentalLocation
```

#### Target

```text
RentalDW.MiniProject.DimGeography
```

#### Load logic

The procedure:

1. Drops the `FactSales` foreign key to `DimGeography`.
2. Selects rental locations from the operational `RentalLocation` table.
3. Inserts only locations that do not already exist in `DimGeography`.
4. Generates new surrogate keys using `MAX(geography_key) + ROW_NUMBER()`.
5. Recreates the `FactSales` foreign key to `DimGeography`.
6. Updates `ETL_Control.last_run` for `usp_Load_DimGeography`.

#### Source-to-target mapping

| Target column | Source / logic |
| --- | --- |
| `geography_key` | Generated warehouse surrogate key. |
| `rentallocation_id` | `RentalLocation.rentallocation_id`. Operational alternate key. |
| `name` | `RentalLocation.name`. |
| `address` | `RentalLocation.address`. |
| `city` | `RentalLocation.city`. |
| `country` | `RentalLocation.country`. |
| `is_manned` | `RentalLocation.is_manned`. |

#### Incremental behavior

New rental locations are identified using:

```sql
WHERE NOT EXISTS (
    SELECT 1
    FROM MiniProject.DimGeography dg
    WHERE dg.rentallocation_id = rl.rentallocation_id
)
```

This makes the location load insert-only and idempotent for existing `rentallocation_id` values.

#### Notes

- The current ETL script loads `rentallocation_id` but does not load `employee_id` into `DimGeography`.
- If the agreed alternate key for `DimGeography` is `(rentallocation_id, employee_id)`, then `employee_id` should also be added to the `DimGeography` table and loaded by this procedure.
- Dropping and recreating the foreign key is usually not required for insert-only dimension loading. In a production-style process, the preferred pattern is to load dimensions before facts and keep foreign keys enabled.
- Existing location rows are not updated if name, address, city, country, or `is_manned` changes in the operational database.

### `MiniProject.usp_Load_DimItem`

Loads rentable item data into `DimItem`.

#### Sources

```text
RentalOperationsDB.MiniProject.Item
RentalOperationsDB.MiniProject.Model
RentalOperationsDB.MiniProject.EquipmentCategory
RentalOperationsDB.MiniProject.MaintenanceRecord
```

#### Target

```text
RentalDW.MiniProject.DimItem
```

#### Load logic

The procedure:

1. Reads physical items from the operational `Item` table.
2. Joins each item to its `Model`.
3. Joins each model to its `EquipmentCategory`.
4. Left joins the latest maintenance record per item.
5. Inserts only items that do not already exist in `DimItem`.
6. Generates new surrogate keys using `MAX(item_key) + ROW_NUMBER()`.
7. Updates `ETL_Control.last_run` for `usp_Load_DimItem`.

#### Maintenance logic

The latest maintenance record is selected using the maximum `maintenance_id` per `item_id`:

```sql
SELECT MAX(maintenance_id)
FROM RentalOperationsDB.MiniProject.MaintenanceRecord
GROUP BY item_id
```

This means `DimItem` stores maintenance context as a descriptive item attribute rather than as a separate maintenance fact table.

#### Source-to-target mapping

| Target column | Source / logic |
| --- | --- |
| `item_key` | Generated warehouse surrogate key. |
| `item_id` | `Item.item_id`. Operational alternate key. |
| `model_id` | `Item.model_id`. |
| `category_id` | `Model.category_id`. |
| `serial_number` | `Item.serial_number`. |
| `status` | `Item.status`. |
| `is_usable` | `Item.is_usable`. |
| `model_name` | `Model.name`. |
| `model_brand` | `Model.brand`. |
| `category_name` | `EquipmentCategory.name`. |
| `hourly_rate` | `Model.hourly_rate`. |
| `maintenance_id` | Latest `MaintenanceRecord.maintenance_id` per item, if available. |
| `maintenance_start` | Latest `MaintenanceRecord.maintenance_start`, if available. |
| `maintenance_end` | Latest `MaintenanceRecord.maintenance_end`, if available. |
| `maintenance_type` | Latest `MaintenanceRecord.type`, if available. |
| `maintenance_cost` | Latest `MaintenanceRecord.cost`, if available. |

#### Incremental behavior

New items are identified using:

```sql
WHERE NOT EXISTS (
    SELECT 1
    FROM MiniProject.DimItem di
    WHERE di.item_id = i.item_id
)
```

This makes the item load insert-only and idempotent for existing `item_id` values.

#### Notes

- The current ETL inserts one `DimItem` row per item.
- New maintenance records for an existing item will not update the existing `DimItem` row because updates are not implemented.
- If the agreed alternate key is `(item_id, model_id, category_id, maintenance_id)`, the ETL logic should be aligned with that grain. The current `NOT EXISTS` condition only checks `item_id`, which means a later maintenance record does not create a new dimension row.
- For detailed maintenance analytics, a separate `FactMaintenance` table would be cleaner than storing maintenance events inside `DimItem`.
- Existing item, model, category, status, usability, or price changes are not currently reflected after the first load.

### `MiniProject.usp_Load_FactSales`

Loads rental transaction line records into `FactSales`.

#### Sources

```text
RentalOperationsDB.MiniProject.RentalTransaction
RentalOperationsDB.MiniProject.RentalTransactionLines
```

#### Dimension lookups

```text
RentalDW.MiniProject.DimCustomer
RentalDW.MiniProject.DimDate
RentalDW.MiniProject.DimGeography
RentalDW.MiniProject.DimItem
```

#### Target

```text
RentalDW.MiniProject.FactSales
```

#### Load logic

The procedure:

1. Reads the previous `last_run` value for `usp_Load_FactSales` from `ETL_Control`.
2. Joins rental transaction headers to rental transaction lines.
3. Looks up the customer surrogate key from `DimCustomer`.
4. Looks up the rental start date key from `DimDate`.
5. Looks up the rental end date key from `DimDate` when an end date exists.
6. Looks up the pickup location key from `DimGeography`.
7. Looks up the rented item key from `DimItem`.
8. Inserts only new transaction lines.
9. Updates `ETL_Control.last_run` for `usp_Load_FactSales`.

#### Source-to-target mapping

| Target column | Source / logic |
| --- | --- |
| `transaction_id` | `RentalTransaction.transaction_id`. Operational alternate key. |
| `transactionline_id` | `RentalTransactionLines.transactionline_id`. Operational alternate key. |
| `customer_key` | Lookup from `DimCustomer` using `RentalTransaction.customer_id = DimCustomer.customer_id`. |
| `startdate_key` | Lookup from `DimDate` using `CAST(RentalTransaction.rental_start AS DATE) = DimDate.date`. |
| `enddate_key` | Lookup from `DimDate` using `CAST(RentalTransaction.rental_end AS DATE) = DimDate.date`. Nullable for active or open rentals. |
| `geography_key` | Lookup from `DimGeography` using `RentalTransaction.pickup_location_id = DimGeography.rentallocation_id`. |
| `item_key` | Lookup from `DimItem` using `RentalTransactionLines.item_id = DimItem.item_id`. |
| `total_amount` | `RentalTransaction.total_amount`. Header-level transaction total. |
| `price` | `RentalTransactionLines.line_amount`. Line-level rental amount. |
| `start_time` | `CAST(RentalTransaction.rental_start AS TIME)`. |
| `end_time` | `CAST(RentalTransaction.rental_end AS TIME)`. Nullable for active or open rentals. |

#### Incremental behavior

The fact load uses two filters.

First, it loads only rentals that started after the previous `FactSales` ETL run:

```sql
WHERE rt.rental_start > @last_run
```

Second, it prevents duplicate fact rows by checking the operational transaction line key:

```sql
AND NOT EXISTS (
    SELECT 1
    FROM MiniProject.FactSales f
    WHERE f.transaction_id     = rt.transaction_id
      AND f.transactionline_id = rtl.transactionline_id
)
```

This supports insert-only incremental loading for new rental transaction lines.

#### Notes

- `FactSales` uses `transaction_id` and `transactionline_id` as operational alternate keys.
- The warehouse surrogate keys are still used for joins from the fact table to dimensions.
- `geography_key` currently represents the pickup location. Return location is not loaded into the current `FactSales` design.
- `total_amount` is a transaction-level value. Because `FactSales` has one row per transaction line, `total_amount` is repeated across all lines in the same transaction. For revenue reporting at line grain, `SUM(price)` is usually safer than `SUM(total_amount)`.
- Late-arriving records with `rental_start <= last_run` may not be loaded by the current incremental filter.
- Updates to existing transactions or transaction lines are not currently handled.

### `MiniProject.usp_Run_Full_ETL`

Runs the complete ETL process.

#### Logic

The procedure prints a start timestamp, executes all load procedures, and prints an end timestamp:

```sql
EXEC MiniProject.usp_Load_DimDate;
EXEC MiniProject.usp_Load_DimCustomer;
EXEC MiniProject.usp_Load_DimGeography;
EXEC MiniProject.usp_Load_DimItem;
EXEC MiniProject.usp_Load_FactSales;
```

#### Purpose

This wrapper procedure gives the project a single ETL entry point:

```sql
EXEC MiniProject.usp_Run_Full_ETL;
```

## Incremental Loading Strategy

The ETL handles new data incrementally using a combination of operational alternate keys, `NOT EXISTS` checks, and `ETL_Control.last_run`.

| Table | Incremental method | Existing-row updates? |
| --- | --- | --- |
| `DimDate` | Generated calendar range. Current script reloads the date table. | Not applicable. |
| `DimCustomer` | Insert customers whose `customer_id` does not already exist. | No. |
| `DimGeography` | Insert locations whose `rentallocation_id` does not already exist. | No. |
| `DimItem` | Insert items whose `item_id` does not already exist. | No. |
| `FactSales` | Insert transaction lines with `rental_start > last_run` and no existing `(transaction_id, transactionline_id)`. | No. |

Current behavior:

```text
New records are inserted.
Existing records are left unchanged.
```

This is appropriate for the current mini-project scope, but it has important limitations:

- Changed customer contact details are not updated in `DimCustomer`.
- Changed location details are not updated in `DimGeography`.
- Changed item status, usability, model information, hourly rate, or maintenance context is not updated in `DimItem`.
- Modified rental transactions or corrected transaction lines are not updated in `FactSales`.
- Late-arriving facts can be missed if their `rental_start` is earlier than or equal to the stored `last_run` value.

Recommended future improvement:

```text
Implement MERGE-based upserts for Type 1 updates, or implement SCD Type 2 where historical attribute changes should be preserved.
```

## Alternate Keys Used by the ETL

The ETL preserves operational keys in the warehouse so that rows can be traced back to the source system.

| Warehouse table | Operational alternate key | Current ETL usage |
| --- | --- | --- |
| `DimCustomer` | `customer_id` | Used to detect new customers and to look up `customer_key` for facts. |
| `DimGeography` | `rentallocation_id` in the current script. Project design may use `(rentallocation_id, employee_id)`. | Used to detect new locations and to look up `geography_key` for facts. |
| `DimItem` | `item_id` in the current script. Project design may use `(item_id, model_id, category_id, maintenance_id)`. | Used to detect new items and to look up `item_key` for facts. |
| `FactSales` | `(transaction_id, transactionline_id)` | Used to prevent duplicate fact rows. |

The warehouse surrogate keys remain the primary keys used for dimensional joins.

Recommended unique constraints:

```sql
ALTER TABLE MiniProject.DimCustomer
ADD CONSTRAINT AK_DimCustomer_Customer
UNIQUE (customer_id);

ALTER TABLE MiniProject.DimGeography
ADD CONSTRAINT AK_DimGeography_RentalLocation
UNIQUE (rentallocation_id);

ALTER TABLE MiniProject.DimItem
ADD CONSTRAINT AK_DimItem_Item
UNIQUE (item_id);

ALTER TABLE MiniProject.FactSales
ADD CONSTRAINT AK_FactSales_Transaction_Line
UNIQUE (transaction_id, transactionline_id);
```

If the wider alternate keys are used in the final model, the table definitions and ETL load logic should be adjusted accordingly:

```sql
-- Example if employee_id is included in DimGeography
UNIQUE (rentallocation_id, employee_id);

-- Example if maintenance context is included in DimItem grain
UNIQUE (item_id, model_id, category_id, maintenance_id);
```

## Data Quality and Validation Ideas

Validation should be run after executing `usp_Run_Full_ETL`.

### 1. Check ETL control timestamps

```sql
SELECT *
FROM MiniProject.ETL_Control
ORDER BY procedure_name;
```

Expected result:

- One row per ETL procedure.
- `last_run` updated for each procedure after a successful run.

### 2. Compare fact row count to source transaction lines

```sql
SELECT COUNT(*) AS source_transaction_lines
FROM RentalOperationsDB.MiniProject.RentalTransaction rt
JOIN RentalOperationsDB.MiniProject.RentalTransactionLines rtl
    ON rt.transaction_id = rtl.transaction_id;

SELECT COUNT(*) AS warehouse_fact_rows
FROM RentalDW.MiniProject.FactSales;
```

The counts should match when the warehouse has been fully loaded and all source rows are within the supported date range.

### 3. Compare line-level revenue

```sql
SELECT SUM(rtl.line_amount) AS source_line_revenue
FROM RentalOperationsDB.MiniProject.RentalTransactionLines rtl;

SELECT SUM(price) AS warehouse_line_revenue
FROM RentalDW.MiniProject.FactSales;
```

Use `price` for line-level revenue validation because it maps to `RentalTransactionLines.line_amount`.

### 4. Check for duplicate fact rows

```sql
SELECT
    transaction_id,
    transactionline_id,
    COUNT(*) AS row_count
FROM RentalDW.MiniProject.FactSales
GROUP BY transaction_id, transactionline_id
HAVING COUNT(*) > 1;
```

Expected result:

```text
No rows returned.
```

### 5. Check for missing dimension lookups

```sql
SELECT COUNT(*) AS fact_rows_with_missing_customer
FROM RentalDW.MiniProject.FactSales
WHERE customer_key IS NULL;

SELECT COUNT(*) AS fact_rows_with_missing_item
FROM RentalDW.MiniProject.FactSales
WHERE item_key IS NULL;

SELECT COUNT(*) AS fact_rows_with_missing_geography
FROM RentalDW.MiniProject.FactSales
WHERE geography_key IS NULL;

SELECT COUNT(*) AS fact_rows_with_missing_start_date
FROM RentalDW.MiniProject.FactSales
WHERE startdate_key IS NULL;
```

Expected result:

```text
All counts should be 0.
```

`enddate_key` may be null if active rentals are allowed and `rental_end` is not yet known.

### 6. Check dimension row counts against operational source tables

```sql
SELECT COUNT(*) AS source_customers
FROM RentalOperationsDB.MiniProject.Customer;

SELECT COUNT(*) AS dim_customers
FROM RentalDW.MiniProject.DimCustomer;

SELECT COUNT(*) AS source_locations
FROM RentalOperationsDB.MiniProject.RentalLocation;

SELECT COUNT(*) AS dim_geographies
FROM RentalDW.MiniProject.DimGeography;

SELECT COUNT(*) AS source_items
FROM RentalOperationsDB.MiniProject.Item;

SELECT COUNT(*) AS dim_items
FROM RentalDW.MiniProject.DimItem;
```

For insert-only loads, dimension counts should match the number of loaded operational business keys.

## SQL Server Implementation Notes

### Surrogate key generation

The ETL generates surrogate keys using this pattern:

```sql
ISNULL((SELECT MAX(key_column) FROM target_table), 0)
+ ROW_NUMBER() OVER (ORDER BY source_business_key)
```

This works for a controlled mini-project ETL process. In a production environment, identity columns or sequences are usually safer because `MAX() + ROW_NUMBER()` can be risky if multiple ETL sessions run at the same time.

### Foreign key handling in `DimGeography`

`usp_Load_DimGeography` currently drops and recreates this constraint:

```text
FK_FactSales_DimGeography
```

For this project, the procedure can work if the constraint exists with that exact name and the user has permission to alter the table.

Recommended improvement:

```text
Keep foreign keys enabled and load dimensions before facts instead of dropping constraints during normal ETL runs.
```

### Date dimension reload

`usp_Load_DimDate` uses `DELETE FROM MiniProject.DimDate` before inserting dates again.

Recommended improvement:

```text
Maintain DimDate as a stable calendar table and append only missing dates when needed.
```

This avoids unnecessary deletes and reduces the risk of conflicts with fact table foreign keys.

### Transaction handling

The script includes development/testing transaction commands:

```sql
BEGIN TRAN
...
ROLLBACK
COMMIT
```

For final execution, the script should not include both `ROLLBACK` and `COMMIT` after the same transaction. Choose the correct behavior depending on the purpose:

| Scenario | Recommended action |
| --- | --- |
| Testing the ETL without saving changes | Use `ROLLBACK`. |
| Running the ETL and saving changes | Use `COMMIT`. |
| Production-style ETL | Use `TRY...CATCH` with explicit `BEGIN TRAN`, `COMMIT`, and `ROLLBACK` on error. |

A future version should add structured error handling, for example:

```sql
BEGIN TRY
    BEGIN TRAN;

    EXEC MiniProject.usp_Run_Full_ETL;

    COMMIT;
END TRY
BEGIN CATCH
    IF @@TRANCOUNT > 0
        ROLLBACK;

    THROW;
END CATCH;
```

### Development reset of `last_run`

The script includes this reset section:

```sql
UPDATE RentalDW.MiniProject.ETL_Control
SET last_run = '2023-01-01';

EXEC MiniProject.usp_Run_Full_ETL;
```

This is useful for development or testing because it forces the fact load to treat older source data as new.

This reset should not be included in normal production execution unless a controlled reload is intended.

### DDL inside the ETL script

The script includes this statement:

```sql
ALTER TABLE MiniProject.FactSales
    ALTER COLUMN price DECIMAL(18,2) NULL;
```

This is a schema change rather than a load step. A cleaner structure is to keep table definitions and column changes in the warehouse DDL scripts, while ETL scripts focus on loading data.

## Reporting Notes

The loaded star schema supports reporting questions such as:

- Revenue by date, month, quarter, or year.
- Revenue by customer country or city.
- Revenue by rental pickup location.
- Revenue by equipment category, model, or brand.
- Number of rented items by item status or category.
- Rental activity by start time and end time.
- Rental activity for manned versus unmanned locations.

Important measure rule:

```text
For line-level revenue, use SUM(FactSales.price).
```

Avoid summing `FactSales.total_amount` directly at line grain unless the measure logic accounts for duplicated transaction totals.

## Known Limitations

The current ETL is appropriate for a mini-project implementation, but it has some known limitations.

| Area | Current limitation | Recommended improvement |
| --- | --- | --- |
| Dimension updates | Existing dimension rows are not updated. | Use `MERGE` for Type 1 updates or SCD Type 2 for history. |
| Fact updates | Existing fact rows are not updated if source transactions are corrected. | Use `MERGE` based on `(transaction_id, transactionline_id)`. |
| Late-arriving facts | Facts with `rental_start <= last_run` may be missed. | Use source `created_at`/`modified_at` timestamps or a rolling lookback window. |
| Maintenance history | Only latest maintenance context is considered during item insert. | Add `FactMaintenance` or implement SCD Type 2 for `DimItem`. |
| Geography key | Current script uses `rentallocation_id`; design may require `(rentallocation_id, employee_id)`. | Add and load `employee_id` if it is part of the alternate key. |
| Surrogate keys | Keys are generated with `MAX() + ROW_NUMBER()`. | Use identity columns or sequences for safer key generation. |
| Foreign key handling | `DimGeography` load drops and recreates a fact foreign key. | Keep FKs enabled and rely on correct load order. |
| Date dimension | Current procedure deletes and reloads date rows. | Maintain `DimDate` as a stable calendar dimension. |
| Error handling | No complete `TRY...CATCH` framework around the full ETL. | Add transaction-safe error handling and ETL audit logging. |

## Recommended Next Improvements

### 1. Add `MERGE` statements for Type 1 updates

For dimensions where historical changes do not need to be preserved, use `MERGE` to update changed attributes and insert new records.

Good candidates:

- `DimCustomer`
- `DimGeography`
- selected `DimItem` attributes

### 2. Implement SCD Type 2 for historical dimension tracking

If reports need to show facts according to the dimension values that were valid at rental time, implement SCD Type 2 columns such as:

| Column | Purpose |
| --- | --- |
| `valid_from` | Start timestamp for the dimension version. |
| `valid_to` | End timestamp for the dimension version. |
| `is_current` | Indicates the current active version. |

SCD Type 2 is most useful for attributes such as customer address, item status, item model details, and location information.

### 3. Improve the fact incremental filter

The current fact load uses:

```sql
rt.rental_start > @last_run
```

This works for simple new rentals, but it can miss late-arriving records.

A stronger pattern is to add source audit columns such as:

```text
created_at
updated_at
```

Then filter based on source modification time instead of business event time.

### 4. Add ETL audit logging

Create an audit table that stores each ETL run with:

- ETL run ID
- procedure name
- start time
- end time
- inserted row count
- updated row count
- failed row count
- status
- error message

This makes troubleshooting easier and provides a more complete ETL history than `ETL_Control.last_run` alone.

### 5. Separate schema deployment from ETL execution

Move statements such as `CREATE TABLE`, `ALTER TABLE`, and constraint changes into schema deployment scripts.

Recommended folder separation:

```text
/sql/warehouse/create_tables.sql
/sql/warehouse/create_constraints.sql
/etl/SQL-ETL-procedures.sql
/etl/run_full_etl.sql
/etl/validation/validation_queries.sql
```

## How to Run the ETL

1. Create the operational database and load the operational source data.
2. Create the data warehouse tables and constraints.
3. Open `SQL-ETL-procedures.sql` in SSMS.
4. Make sure the script is running against the correct server and can access both databases:

```text
RentalOperationsDB
RentalDW
```

5. Execute the procedure creation script.
6. Run the full ETL:

```sql
EXEC MiniProject.usp_Run_Full_ETL;
```

7. Check the control table:

```sql
SELECT *
FROM MiniProject.ETL_Control;
```

8. Run validation queries to compare the operational database and warehouse totals.

## Design Summary

The ETL process loads the rental data warehouse from the operational database using a clear stored procedure structure. Dimension tables are loaded before the fact table, and operational keys are preserved as alternate keys for traceability and lookup logic.

The current design supports insert-only incremental loading for new business records. This is sufficient for the mini-project and makes the process easy to understand, rerun, and validate. The next natural improvement is to add update handling through `MERGE` statements or SCD Type 2 logic, especially for customer, geography, item, and maintenance-related attributes.
